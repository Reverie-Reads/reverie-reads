# Pro beta program

Status: owner-approved product sequence, 2026-09-10. This is the active program contract; it does
not itself grant access, invite readers, change production data, or authorize billing.

## Purpose

Reverie will give a bounded beta cohort Pro access without payment, learn which forms of depth
readers understand and return to, reduce the product around that evidence, and add billing only
after the retained offer is clear.

The beta is successful if it produces a smaller, more legible product decision. Shipping every
candidate feature unchanged is not a success condition.

## Access contract

- No payment method, checkout, recurring agreement, automatic conversion, or charge.
- A service-managed beta grant is distinct from a subscription row and corpus-administrator status.
- The server includes an active beta grant as positive Pro proof for every premium mutation.
- Removing or ending a grant blocks new premium writes without deleting books or reader-authored
  premium data. Preserve export and an honest read-only view where data would otherwise disappear.
- Invitations state the access period and post-beta treatment before enrollment.
- Account deletion removes the grant and every owner-scoped beta artifact through the established
  deletion boundary.

Implementation belongs in the private overlay. The public host may expose only the narrow
entitlement and registration seams required for a complete Free build.

## Candidate portfolio

Test one coherent experience in each value family:

1. **Collection depth:** the shipped Connected Universes and Edition Lens.
2. **Atmosphere authorship:** a bounded room workshop that starts from the nine shipped rooms and
   lets the reader make a saved, contrast-safe variant. The existing nine rooms and adaptive palette
   remain Free.
3. **Decision depth:** deeper taste explanation, taste-over-time, or mood-aware planning. Choose the
   smallest slice that can be used repeatedly without pretending uncertain book metadata is fact.
4. **Private reflection:** a reader-controlled annual keepsake built from recorded history. Saving or
   sharing is an explicit reader action; no public profile or automatic publication.

Do not add continuous corpus freshness, unattended sync, native-store billing, broad club
automation, or bookstore analytics to the initial cohort. Those add recurring operations before the
beta has shown what deserves them.

## Evidence

### Content-free product events

For each candidate, record only:

- eligible surface shown;
- opened;
- primary task completed;
- abandoned before completion;
- returned within 7 and 30 days;
- failed or unavailable state;
- optional feedback prompt answered.

Use opaque reader and cohort identifiers. Do not include book ids, ISBNs, titles, contributors,
notes, ratings, moods, taste vectors, history rows, series/universe membership, cover URLs, search
terms, or keepsake contents. Define retention and deletion before the first event is stored.

### Observed sessions

Use the existing five-session reader-validation protocol. Include first use, an unassisted return,
and a short interview covering:

- what the reader believes Pro does;
- which feature they would miss;
- where the feature duplicated another Reverie surface;
- what felt too complex or too private;
- whether they would pay, at what cadence, and why.

Stated willingness to pay is directional. A later paid pilot supplies payment evidence.

## Reduction rule

Review each candidate using comprehension, successful completion, repeat use, qualitative value,
support burden, provider dependency, and operating cost. Then choose one:

- **Keep:** readers understand and return to it with supportable cost.
- **Simplify:** the need is real and the current surface is too complex.
- **Combine:** the behavior belongs inside an existing route rather than another destination.
- **Hide:** useful to a narrow group but distracting as primary navigation.
- **Remove:** little value or unacceptable trust, cost, or maintenance burden.

Removal must preserve compatible reader-authored data for export and must not weaken Free. Record the
decision and evidence without retaining private reading content.

## Billing gate

Payment work begins after all of these are true:

1. The retained Pro offer and Free boundary are written in reader-facing language.
2. Beta evidence supports the retained features and records what was reduced.
3. Provider commercial-use and data-retention decisions cover every retained paid path.
4. Public privacy, terms, support, cancellation, refund, and account-deletion information is ready.
5. The billing event model covers idempotency, replay, renewal, cancellation, refund, dispute,
   lapse, recovery, and account deletion.
6. An entitled, non-entitled, unavailable, revoked, and expired beta account pass the premium smoke
   tests without cross-account data exposure.

Only then select and implement a payment provider. No beta reader is automatically converted into a
paying customer.
